# UI設計: マネージャー専用エリア

## 概要

組織モデルを CEO / マネージャー / 社員 の3層に簡素化したことに伴う新設エリア。

新しいタスクフロー:

```
社長 → 自然言語で指示 → AI秘書が整理・要約 → 該当専門のマネージャー本人へ「指示ブリーフ」を配信
                                                        │
                                                        ▼
                                        マネージャーが指示ブリーフを確認
                                                        │
                                                        ▼
                                    マネージャーがタスクを設計し、指名制で社員に割り当て
                                                        │
                                                        ▼
                                              社員が実行・進捗報告
```

AI秘書はこのフローでは「整理・伝言役」のみを担う。**タスクを自動生成しない**。タスク設計・分解・担当者指名はすべてマネージャーの裁量。

> **既存実装との差分メモ**: 現行の `app/(ceo)/ai-secretary/ai-secretary-client.tsx` は「タスク化して部門AIに振り分ける」ボタンでAIがタスクを直接生成する実装になっている。組織モデル変更後は、この結果表示から「マネージャーに送る」フローへ置き換える必要がある（AI秘書側の変更は本設計書のスコープ外。別途 `system-directive-routing.md` 等での設計を推奨）。

対象画面は3つ。

1. `/manager/inbox` — マネージャー受信箱（指示ブリーフ一覧）
2. `/manager/inbox/[id]` — ブリーフ詳細＋タスク作成
3. 既存 `/settings`（社員設定画面）への「専門(specialty)」追加 — マネージャーのみ表示

---

## 0. 権限・アクセス制御

| ルール | 内容 |
|---|---|
| ルート保護 | `role = 'manager'` のみ `/manager/**` にアクセス可能。CEO/社員はリダイレクト or 403 |
| 表示対象ブリーフ | `directives.target_manager_id = 自分のuser.id` のもののみ表示（他マネージャー宛は見えない） |
| タスク指名先 | 自分の管轄（同じ specialty の社員）を優先表示 + 「全社員から選ぶ」切り替えを許可（小規模組織のため） |
| AI全社指示入力欄 | 置かない（CEO専用の原則を継承） |
| AuditLog | ブリーフのステータス変更（sent→in_progress→done）、タスク作成・指名はすべて記録 |

### 3.3 並び順ルール

1. `status = 'sent'`（未着手）を最上部にグループ化
2. 次に `status = 'in_progress'`（対応中）
3. 最後に `status = 'done'`（完了）— カードは彩度を落として視認性を下げる
4. 各グループ内は `created_at` 降順（新しいものが上）

### 3.4 コンポーネント構成

| コンポーネント | 役割 |
|---|---|
| `InboxHeader` | タイトル・説明文・未対応件数バッジ |
| `StatusFilterTabs` | すべて/未着手/対応中/完了 の絞り込み（件数バッジ付き、既存 `TaskList` のフィルタUIパターンを踏襲） |
| `DirectiveCard` | 1件のブリーフをカード表示。状態ドット・カテゴリタグ・タイトル・AI要約1〜2行・受信日時・詳細リンク |
| `EmptyState` | 該当ブリーフが0件のときの案内 |

### 3.5 DirectiveCard 表示要素

| 要素 | データソース | 表示 |
|---|---|---|
| 状態ドット + ラベル | `status` | 🟠未着手 / 🟢対応中 / ⚪完了（テキストバッジ、色は §1 のトークン） |
| カテゴリタグ | `category` | 例: 「営業」「開発」pill バッジ（`bg-teal-50 text-teal-700`） |
| タイトル | `organized_title` | 太字1行、省略記号 |
| 要約 | `organized_summary` | 2行までクランプ、グレートーン |
| 受信日時 | `created_at` | JST表示（`lib` のJST日付ヘルパーを利用） |
| CTA | — | 「詳細を見る →」ボタン → `/manager/inbox/[id]` |

### 3.6 状態

- **通常状態**: 上記グルーピングでカード表示
- **空状態（0件）**: 「まだ届いている指示ブリーフはありません。社長からの指示がAI秘書経由で届くとここに表示されます」（アイコン: 受信箱アイコンをグレーで中央配置、CEO側 `!result && !loading` の空状態パターンを踏襲）
- **フィルタ結果0件**: 「該当するブリーフはありません」（`TaskList` の空状態文言パターンを踏襲）
- **ローディング**: Server Component でデータ取得するためスケルトンは基本不要。件数バッジのみ楽観的でなく確定値を表示。

### 3.7 必要なデータ取得

```ts
// app/(manager)/inbox/page.tsx（Server Component）
// Supabaseから directives を取得
select: id, raw_instruction, category, organized_title, organized_summary,
        organized_body, check_items, target_manager_id, status, created_at
where: target_manager_id = currentUser.id
order: status優先順位（sent → in_progress → done） + created_at desc
```

件数バッジ用に `sent` の件数を別途カウント（サイドバーの受信箱バッジにも使う）。

### 4.3 コンポーネント構成

| コンポーネント | 役割 |
|---|---|
| `BriefHeader` | ステータスバッジ・カテゴリ・タイトル・受信日時、戻るリンク |
| `BriefBodyCard` | `organized_body` を表示。`raw_instruction`（社長の原文）は `<details>` 的な折りたたみで参照用に表示（改ざん防止・文脈確認のため） |
| `CheckItemsCard` | `check_items[]` を確認事項リストとして表示（チェックボックスではなく、あくまで注意喚起の読み上げ用。マネージャーが対応済みか目視するだけで良く、DBに状態を持たせる要件は今回スコープ外） |
| `StatusControl` | ブリーフの `status` を `sent → in_progress → done` に更新するボタン群。CEOの承認UIの操作感（明確なボタン、確認なしで即時反映＋トースト）を踏襲 |
| `CreatedTasksList` | このブリーフ (`directive_id`) から作成済みの `tasks` を一覧表示。既存 `TaskList` の進捗円+バーのミニ版を使う |
| `CreateTaskForm` | タスク作成フォーム本体（詳細は4.4） |
| `AssigneeSelect` | 担当社員セレクト。「自分の管轄のみ／全社員」トグル付き |
| `ChecklistBuilder` | 任意のチェックリスト入力（タイトル＋重み%、動的追加/削除、合計%表示） |

### 4.4 タスク作成フォーム 項目定義

| 項目 | 型 | 必須 | 備考 |
|---|---|---|---|
| タイトル | text | ○ | `tasks.title` |
| 説明 | textarea | − | `tasks.description` |
| 優先度 | pill選択（低/中/高/緊急） | ○ | `tasks.priority`、デフォルト `medium` |
| 期限 | date | − | `tasks.due_date` |
| 担当社員（指名） | select | ○ | `tasks.assigned_to`。**自動割当ではなく必ず人が選ぶ** |
| 担当絞り込み | ラジオ | − | 「自分の管轄のみ」= 同じ `specialty` の社員 / 「全社員から選ぶ」= 全社員 |
| チェックリスト | 動的リスト（任意） | − | `task_checklist_items`。重み合計100%を超えたら警告表示（保存はブロックしない、赤字で「合計が100%を超えています」） |

**送信時の挙動**:
- `directive_id` に現在表示中のブリーフIDを自動セット
- `created_by` = マネージャー自身
- `provisional_score` は今回スコープ外（既存の点数ロジックは維持するが、AI自動算出ではなくマネージャー任意入力 or 後続フェーズで対応。本設計書では入力欄を設けない）
- 作成成功後: フォームをリセットし、`CreatedTasksList` を再取得・先頭に追加表示。トースト「タスクを作成し、○○さんに割り当てました」
- ブリーフの `status` が `sent` のままなら、タスクを1件でも作成した時点で自動的に `in_progress` に更新（確認ダイアログなし、バックグラウンドで実施）

### 4.5 状態・空状態

| 状態 | 表示 |
|---|---|
| `CreatedTasksList` が0件 | 「まだこのブリーフからタスクは作成されていません。下のフォームから最初のタスクを作成してください」 |
| フォーム送信中 | ボタンを `disabled` にし「作成中...」+ スピナー（CEO側 `AiSecretaryClient` の `Loader2` パターンを踏襲） |
| 担当社員が0人（管轄内に社員がいない） | セレクト内に「管轄内に社員がいません。『全社員から選ぶ』に切り替えてください」を表示し、トグルを自動的に全社員側へ促す |
| ブリーフが既に `done` | フォーム自体は引き続き使用可（完了後の追加タスクも許容）だが、ヘッダーに「このブリーフは完了扱いです」の淡いグレー注記を出す |
| 不正アクセス（他マネージャー宛のブリーフID） | 404 相当のエラーページへリダイレクト |

### 4.6 必要なデータ取得 / Server Action

**データ取得（page.tsx）**
```
1. directives を id 指定・target_manager_id = currentUser.id で1件取得
   → 該当なし or 権限外なら notFound()
2. tasks を directive_id = directives.id で一覧取得
   （title, priority, due_date, progress_rate, status, assigned_to → users.full_name join）
3. users を specialty = currentUser.specialty かつ role = 'employee' で一覧取得（管轄社員）
4. users を role = 'employee' で全件取得（全社員セレクト用、名前・specialtyのみ）
```

**Server Actions（actions.ts）**
```ts
updateDirectiveStatus(directiveId: string, status: 'sent' | 'in_progress' | 'done')
  // 権限チェック: currentUser.id === directive.target_manager_id
  // AuditLog: action='directive.status_changed'

createTaskFromDirective(input: {
  directiveId: string;
  title: string;
  description?: string;
  priority: 'low'|'medium'|'high'|'urgent';
  dueDate?: string;
  assignedTo: string;           // 指名必須
  checklist?: { title: string; weight: number }[];
})
  // tasks に insert（created_by = currentUser.id, directive_id, department_id は
  //   currentUser.specialty から解決 or 廃止して null 許容にするか要確認）
  // checklist があれば task_checklist_items に insert
  // directive.status が 'sent' なら 'in_progress' に自動更新
  // AuditLog: action='task.created_by_manager'
  // Notification: assignedTo 宛に 'task_assigned' 通知を作成
```

## 5. 画面3: マイページ設定への「専門」追加

### 5.1 方針

既存の `app/(employee)/settings/settings-client.tsx` を拡張する。新規画面は作らない。`role = 'manager'` のユーザーにのみ「専門」セクションを表示する（社員には表示しない。社員側は既存の「担当業務（複数選択）」セクションをそのまま維持）。

### 5.2 ワイヤーフレーム（追加セクションのみ）

```
┌──────────────────────────────────────────┐
│ 🎯 専門（マネージャー専用）                    │
│ あなたが管轄する専門領域を1つ選択してください。   │
│ 社長からの指示ブリーフは、この専門に基づいて     │
│ あなた宛に振り分けられます。                    │
│                                            │
│  ( ) 営業     ( ) 開発     ( ) 案件管理       │
│  ( ) 経理・請求  ( ) 事務・オペレーション        │
│  ( ) その他（自由入力）→ [___________________] │
│                                            │
│  ⚠ 1つの専門につき担当マネージャーは1人です。   │
│    既に他の人が選択している専門は選べません。    │
│                                            │
│              [専門を更新する]                │
└──────────────────────────────────────────┘
```

### 5.3 仕様詳細

| 項目 | 内容 |
|---|---|
| 表示条件 | `currentUser.role === 'manager'` の場合のみ表示（社員・CEOには非表示） |
| 選択形式 | ラジオボタン（単一選択）。既存の「担当業務」トグルピルとは意図的に見た目を変え、**1人1専門**であることを視覚的に強調する |
| プリセット選択肢 | 営業 / 開発 / 案件管理 / 経理・請求 / 事務・オペレーション（既存 `departments` マスタの `display_name` を流用可能） |
| 自由入力 | 「その他」を選んだ場合のみテキスト入力欄を活性化 |
| 排他制御 | 選択しようとした専門が既に別のマネージャーに割り当て済みの場合、送信時にサーバー側でエラーを返す（「この専門は既に○○さんが担当しています」）。フォーム側は選択自体は許可し、送信時バリデーションで防ぐ（他マネージャーの現在の専門をクライアントに一覧で持たせない = 情報露出を避けるため） |
| 更新後の反映 | `router.refresh()` でサイドバー等の表示を最新化。成功メッセージは既存 `StatusMessage` コンポーネントを再利用 |

### 5.4 必要なデータ取得 / Server Action

```ts
// page.tsx 側で currentUser.role === 'manager' の場合のみ渡す
// 既存の specialty 値（あれば）を initialSpecialty として渡す

// actions.ts に追加
updateSpecialty(userId: string, specialty: string)
  // 権限チェック: userId === currentUser.id かつ role === 'manager'
  // 重複チェック: 他の manager が同じ specialty を持っていないか確認
  //   （users テーブルに specialty カラムを追加する想定。UNIQUE制約は
  //     role='manager' の場合のみ有効にしたいため、アプリ側バリデーション
  //     + 部分UNIQUEインデックス(WHERE role='manager')の両方を推奨）
  // AuditLog: action='user.specialty_changed'
```

> **スキーマ差分メモ**: `.claude/designs/02-erd.md` の `users` テーブルに `specialty TEXT` カラムを追加する必要がある。また `roles` に `'manager'` を追加（現行は ceo/admin/employee/viewer の4種）。さらに `directives` テーブルは ERD に存在しないため新規追加が必要（`id, raw_instruction, category, organized_title, organized_summary, organized_body, check_items TEXT[], target_manager_id, status, created_by, created_at, updated_at`）。これらはDB設計書側の別途更新が必要（本ドキュメントはUI設計のみのためスキーマ変更の実施はスコープ外、次アクションで案内）。

## 7. インタラクション早見表

| 操作 | 結果 |
|---|---|
| 受信箱でブリーフカードをクリック | `/manager/inbox/[id]` へ遷移 |
| フィルタタブ切り替え | クライアント側でリスト絞り込み（再フェッチなし） |
| ブリーフ詳細で「対応中に変更」 | `updateDirectiveStatus` 実行 → バッジが即時 teal に変化、トースト表示 |
| ブリーフ詳細で「完了にする」 | 確認なしで `status='done'` に更新（Undo可能なようトーストに「元に戻す」を5秒間表示することを推奨） |
| タスク作成フォーム送信 | バリデーション（タイトル・優先度・担当社員必須）→ 成功時トースト＋一覧に反映＋フォームリセット。ブリーフが `sent` なら自動的に `in_progress` へ |
| 担当社員セレクトのトグル切替 | 「自分の管轄のみ」⇔「全社員から選ぶ」でセレクトの選択肢リストを即時入れ替え（選択済みの値が新リストに無ければクリア） |
| チェックリスト「+項目を追加」 | 空の行を1件追加（デフォルト重み0%） |
| チェックリスト合計が100%超過 | 保存はブロックしないが赤字警告テキストを表示（既存 `TaskChecklistItem` の重み思想に合わせ、100%ちょうどが理想だが厳密バリデーションはしない） |
| 設定画面で専門を選んで更新 | 重複していれば赤エラーメッセージ、成功時は緑メッセージ＋`router.refresh()` |
